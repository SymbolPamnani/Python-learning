CUSTOMER CHURN PREDICTION — CONCEPTS & LEARNING NOTES
======================================================

PROJECT OVERVIEW
----------------
Built an end-to-end machine learning system to predict whether a customer
is likely to churn (leave a company's service).

The project covers the complete ML workflow:
EDA → preprocessing → model experimentation → validation → threshold
optimization → final model → serialization → prediction → Streamlit app.


1. UNDERSTANDING THE DATA
-------------------------
The dataset contains 1,000 customers and a binary target:

    Churn = 0 → Customer stayed
    Churn = 1 → Customer churned

The dataset is imbalanced:
    849 non-churned
    151 churned

This immediately showed why accuracy alone should not be trusted.


2. DATA EXPLORATION & FEATURE ANALYSIS
--------------------------------------
Performed:
- Dataset shape and structure inspection
- Data type analysis
- Statistical summaries
- Missing-value analysis
- Target distribution analysis
- Churn proportion analysis

A major lesson was that not every column should automatically be given
to the model.


3. DATA LEAKAGE — AN IMPORTANT LESSON
-------------------------------------
Cancellation_Date initially appeared useful, but it was only available
for customers who had already churned.

Using it would allow the model to indirectly see the answer it was
supposed to predict.

Therefore:

    Cancellation_Date → removed

Customer_ID was also removed because it is an identifier rather than
a meaningful predictive feature.

Lesson:
A feature can look predictive and still be invalid if it contains
information that would only be known after the prediction event.


4. PREPROCESSING
----------------
The dataset contained both numerical and categorical features.

Numerical features:
- Missing values → median imputation
- Scaling → StandardScaler

Categorical features:
- Missing values → most-frequent imputation
- Encoding → OneHotEncoder

ColumnTransformer was used to apply the correct preprocessing to each
feature type.

The preprocessing and model were combined into a Pipeline.

This was important because preprocessing must be learned only from the
training data and then consistently applied to validation, testing,
and future predictions.


5. TRAIN / TEST SPLIT
---------------------
Used:

    train_test_split(..., stratify=y)

with an 80/20 split.

Stratification was used to preserve the churn/non-churn distribution
in both sets.

The test set was kept separate for final evaluation.


6. FIRST MODEL — LOGISTIC REGRESSION
------------------------------------
Logistic Regression was selected as a strong baseline because this is
a binary classification problem and the model is relatively simple
and interpretable.

The initial model showed high accuracy but very poor churn recall.

This exposed an important problem:

    A model can have reasonable accuracy while failing to identify
    the minority class that actually matters.


7. CLASS IMBALANCE
------------------
Because only 15.1% of customers churned, the model naturally had a
tendency to favor the majority class.

To address this, class_weight="balanced" was introduced.

This increased the model's focus on the minority churn class.

The trade-off was expected:
- Recall improved
- Accuracy decreased
- Precision remained relatively low

This was a useful lesson in choosing metrics according to the actual
problem rather than optimizing accuracy blindly.


8. CROSS-VALIDATION
-------------------
5-fold StratifiedKFold cross-validation was introduced to obtain a
more reliable estimate of model performance.

The model was evaluated using:
- Accuracy
- Precision
- Recall
- F1 Score

F1 became particularly important because it balances precision and
recall for the minority churn class.


9. DECISION TREE EXPERIMENT
---------------------------
Decision Trees were tested at multiple depths:

    1, 2, 3, 4, 5, 7, 10, None

Training and validation performance were compared.

The experiment demonstrated how increasing tree depth can improve
training performance while hurting generalization.

For example, an unrestricted tree reached perfect training performance
but performed considerably worse on validation data.

Lesson:
Higher training accuracy does not mean a better model.
The difference between training and validation performance is a useful
indicator of overfitting.


10. MODEL SELECTION
-------------------
Although the Decision Tree was explored in detail, Logistic Regression
was selected as the final model.

The goal was not simply to choose the model with the highest accuracy,
but to build a model with reasonable generalization, interpretability,
and useful churn detection.


11. DECISION THRESHOLD — A KEY IMPROVEMENT
------------------------------------------
A major improvement was realizing that the default classification
threshold of 0.50 does not necessarily suit the business problem.

Instead of simply using:

    probability >= 0.50 → churn

multiple thresholds were tested.

Out-of-fold probabilities were generated using cross-validation so that
threshold selection was based on validation predictions rather than
the final test set.

Thresholds from 0.30 to 0.70 were evaluated using precision, recall,
and F1 score.

The best threshold based on validation F1 was:

    Threshold = 0.60

This demonstrated that model training and decision-making are separate
steps.

The model produces a probability; the threshold determines how that
probability is converted into a final class.


12. A MISTAKE WE CORRECTED
--------------------------
An earlier version selected the threshold using test-set performance.

That was not methodologically correct because the test set should
remain unseen until final evaluation.

The process was therefore changed to:

    Training data
        ↓
    Cross-validation
        ↓
    Out-of-fold probabilities
        ↓
    Threshold selection
        ↓
    Final model training
        ↓
    Unseen test evaluation

This was one of the most important lessons from the project:
the test set should not influence model or threshold decisions.


13. FINAL MODEL
---------------
The final model is:

    Logistic Regression
    class_weight="balanced"
    max_iter=1000

with:

    Decision threshold = 0.60

Final test performance:

    Precision = 0.241
    Recall    = 0.433
    F1 Score  = 0.310

The validation F1 was higher than the final test F1.

Rather than hiding this difference, it was treated as evidence that
validation performance is only an estimate and that performance can
vary on truly unseen data.


14. MODEL SERIALIZATION
-----------------------
The trained model was saved using Joblib:

    models/churn_model.pkl

The optimized threshold was saved separately:

    models/threshold.txt

This separates model training from prediction and allows the trained
model to be reused without retraining every time.


15. PREDICTION PIPELINE
-----------------------
A separate prediction script was created to:

- Load the trained model
- Load the optimized threshold
- Accept customer information
- Generate churn probability
- Apply the saved threshold
- Return the final prediction

This converted the project from a training experiment into a reusable
prediction system.


16. STREAMLIT APPLICATION
-------------------------
A Streamlit interface was added so users can enter customer information
through a graphical interface.

The application displays:

- Churn probability
- Decision threshold
- Churn prediction
- Risk interpretation

The app loads the serialized model and threshold instead of retraining
the model.

This completed the transition from:

    ML experiment → usable application


17. ENGINEERING IMPROVEMENT — PORTABLE PATHS
--------------------------------------------
The first versions used hardcoded paths based on the local computer
directory.

This worked on the development machine but would fail when the project
was cloned elsewhere.

The paths were changed to use the project directory dynamically.

Lesson:
A project should not depend on the developer's personal file system.


18. KEY LESSONS FROM THE PROJECT
--------------------------------
The most important lessons were not just about algorithms.

I learned to:

- Question whether features are actually valid for prediction
- Detect and remove target leakage
- Handle missing numerical and categorical data correctly
- Use pipelines to prevent preprocessing mistakes
- Understand class imbalance
- Choose metrics based on the problem
- Use cross-validation instead of relying on one split
- Recognize overfitting through train/validation differences
- Understand that probability thresholds are tunable
- Never use the test set to make model decisions
- Save models for later inference
- Separate training from prediction
- Build a usable interface around an ML model
- Make project paths portable
- Document both successful decisions and mistakes


FINAL TAKEAWAY
--------------
This project moved beyond simply training a machine learning model.

The main learning was understanding the complete lifecycle of an ML
solution:

    Understand the data
          ↓
    Clean and validate the features
          ↓
    Build preprocessing correctly
          ↓
    Establish a baseline
          ↓
    Handle real-world problems
          ↓
    Validate and compare models
          ↓
    Optimize the decision process
          ↓
    Evaluate honestly on unseen data
          ↓
    Save the model
          ↓
    Build an application around it

The project reinforced the principle:

    "Understand it before implementing it."

The objective was not to obtain an artificially high score, but to
understand why each decision was made and build a complete, reproducible,
and usable machine learning system.
